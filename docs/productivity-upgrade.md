# v0.2 — 从执行控制台到个人开发工作助手

日期：2026-11-03。范围：可运行的增量升级，不包含邮箱、日历或外部消息发送。

## 第一性原理

个人开发者的稀缺资源是注意力、可连续投入的时间和判断能力。增加 Agent 数量只有在分工明确、上下文完整、结果可以验证时才有收益；否则会增加检查日志、重复说明和处理冲突的时间。

本次设计目标：减少找下一步、重建上下文和识别结果可信度的操作。尚未进行使用时长实验，不能声称效率提高了某个百分比。

采用三个约束：

1. 捕获想法不等于授权执行；准备就绪不等于已经启动。
2. 进程完成、验证命令通过、验收标准满足、批准集成是不同事实。
3. 自动建议必须能够说明依据，并链接到已有的真实操作。不会为了生成日常摘要额外调用收费模型。

## 已实现的闭环

### Capture → Clarify → Launch

首次打开进入 Focus inbox；已有用户保留之前保存的视图。选择项目，输入一句待办，Capture draft 只创建 Mock draft，没有 Session、Run、费用或后台推理。点击 Clarify task 补全目标和可观察的验收条件。满足依赖、节点和本地 Provider 检查后，显示 Review and launch；进入既有启动确认窗口，资源容量仍由调度器检查。

父任务仅用作分组时不推荐直接启动，也不把子任务完成自动解释为父任务已验证。

### Attention queue

每个非归档项目的任务最多一个主要事项，按 recover → approve → fix → waiting → clarify → review → ready 排序；同组按用户任务优先级，再按稳定 ID 排序。这个排序是初始产品假设，不是对个人习惯的机器学习。

- recover：失联 Run，应先检查进程，再使用既有人工对账。
- approve：已有待批准合并，打开对应 Session 的 Diff 与审批 Inspector。
- fix：最近执行失败、中断或取消，先查看历史，再决定续跑。
- waiting：依赖未结束、排队、节点或本地 Provider 状态不满足。
- clarify：叶子任务缺少描述或验收条件，进入编辑。
- review：执行完成但该次结果提交没有精确匹配的批准合并记录。
- ready：已定义结果的未启动任务，进入执行确认。

运行中任务显示总数而不混入决策列表。可以按类型和关键词过滤。普通队列等待仍会显示，这一版没有智能降噪、稍后提醒或 snooze。

### 执行交接包

项目 Working agreements 是用户维护的显式上下文，不是模型自动记忆。可写技术约束、非目标、测试方式；不应写凭证。SQLite 持久化，旧项目默认空。

Run 实际启动并准备工作区后，系统将项目上下文、任务目标、验收条件、验证命令、依赖最近结果提交、上次同任务执行状态/错误、当前指令合成同一 prompt，传给本地或远程 Adapter，并保存 `execution-brief.txt` Artifact。排队期间不会过早冻结尚未结束的依赖状态。原始 Run.prompt 单独保留。

上下文截断按字符，而非 Token：项目 6,000、目标 12,000、验收条件 8,000、验证 argv 8,000、依赖证据 12,000、历史错误 2,000。截断显式标记，当前指令不在这些段落截断范围内。完整项目上下文最多存 12,000 字符。没有自动读取整个仓库或把历史日志无界注入 prompt。

当前交接只引用可核实的元数据，不生成语义化的 Agent 工作总结，也不保证新 Session 自动拥有上个 Session 未合并的代码。依赖代码只有显式 integration 工作区才会合入。prompt 内提示不是安全沙箱，安全边界继续由 Adapter、进程与权限实现。

### 结果证据与回顾

Session 显示 execution state、validation command evidence、approved merge 三个独立字段。命令验证仅信任由 Orchestrator 生成的 `command-validation.json` Artifact；读取出 passed=true 且 exitCode=0 才显示 passed。Agent 自己说“测试通过”或写入同名仓库文件不构成该证据。

完成时冻结 Run.resultCommit。匹配同一 Session 的 Approval.source 才显示已记录合并，避免续跑修改 worktree 后把旧审批套在新结果上。旧 v0.1 Run 没有 resultCommit 时保守显示未知，不回填推断。合并后从建议队列移除的是该精确结果；通过另一个集成 Session 合入的祖先提交目前不会自动识别。

七天回顾基于服务器时间、非归档项目和 Run.endedAt，按运行次数统计 completed、failed、带命令通过、无命令通过。不是任务数，也不是人时节省、成本、完整验收率或生产交付数。批准合并记录不证明代码此刻仍在目标分支（可能之后被用户撤销）。

## 下一阶段的优先级

1. 执行与验收证据绑定到依赖版本，依赖续跑后提示下游需要重新验证。
2. 用户明确维护的结构化交接记录：变更、证据、未解决问题、建议下一步；与模型输出区分来源。
3. 全局在制任务上限、仅异常通知、可撤销的稍后处理，减少多个项目争抢注意力。
4. 浏览器/Windows/实际 SSH 的验收环境，真实 Provider 可选低额度测试。
5. 根据用户实际使用测量澄清到启动时间、结果到决策时间、返工率，再考虑自动规划和更多 Provider。

外部邮箱/日历、无限重试、自动合并、后台付费任务不属于本次范围。
